# Cortex autonomous review protocol — single source of truth

This file is the canonical reference for the autonomous PR review loop. `cortex:review` (standalone) and `cortex:exec` (wrap-up "Ship & autonomous review" task) both point here so the rules live in exactly one place and never drift. When a skill needs to run the loop, read this file and apply it verbatim, in-process — never chain into `cortex:review` via the Skill tool mid-run (no-return-semantics trap). `<PLUGIN_ROOT>` below is the plugin root, as defined by the skill driving the protocol.

## State machine — the PR state IS the process state

- **`draft` = machine-owned.** The loop may commit fixes, push, and post comments.
- **`ready` (non-draft) = human-owned.** The loop never commits to, nor changes the state of, a ready PR — standalone invocation against a ready PR runs **read-only mode** (fan-out + delivery comment only; no fixes, no state flips).
- **Fresh state check before EVERY round**: `gh pr view <num> --json isDraft,state,url`. If the state changed away from the loop's baseline mid-run (human flipped draft→ready, PR closed/merged), **abort the autonomous phase immediately**, post a status comment explaining where the loop stopped, and leave everything else untouched.
- Non-convergence is signalled by state, not prose: the PR **stays draft** with a "needs human" delivery comment. A draft PR at rest = the machine could not finish — or converged but was **blocked from flipping ready by required status checks** — or converged and was **kept draft because the approved scope ends at a draft PR** (the delivery comment says which); all are correct, visible outcomes. Terminal states are exactly four: `ready` · `draft + needs-human` · `draft + converged-blocked-by-checks` · `draft + converged-kept-by-scope` — recorded in the receipt's `terminal` field (`ready` · `draft-needs-human` · `draft-blocked-by-checks` · `draft-kept-by-scope`; read-only mode records `read-only`), because `status: complete` only says the loop reached *a* terminal state, not which one. Readers (`/cortex:status`, `/cortex:end`'s handoff) never assume `ready` from `complete` alone. The five delivery facts and the state → owner → next table live in `<PLUGIN_ROOT>/skills/end/references/delivery-lifecycle.md`.

## Loop overview

```
ship (commit → push → gh pr create --draft)     ← skipped in standalone mode if PR exists
  → preflight (state baseline, branch protection, diff profile, the probe's runner and reuse check §6)
  → Round: fan-out reviewers (parallel, matrix-gated) ‖ the test-run probe in the background; its failures join dedup as seeded findings
  → dedup (lead)
  → debate (high-severity / contested only; seeded test failures exempt)
  → fix batch (one fix-author per disjoint file group, in parallel; lead-only commits) → push → suite re-run ‖ re-run affected reviewers → the round's verdict waits for both
  → converged? → evidence files → delivery comment → gh pr ready   (skipped when required checks or the approved scope keep it draft)
  → after the cap: high / floor-area / medium+ this-loop regression left → advisor round? granted → one more round
                                                                       → not granted → evidence files → delivery comment ("needs human") → PR stays draft
                   anything else left (a low this-loop regression outside the floor areas included) → follow-up rows (non-blocking) → converged
```

The receipt is written after **every** state transition: baseline taken, fan-out returned, dedup done, verdicts recorded, fix round N committed, advisor round decided, evidence written, ready flipped (or deferred/blocked). Every write while the loop runs, from the baseline on, carries `terminal: null` and `completed_at: null`: readers treat that shape as a loop in flight, never a failure, until it sits untouched for 60 minutes or is dated more than 5 minutes in the future, when it reads as stalled. Resume reconciles the receipt against live `git log` and `gh pr view` — **git/GitHub win on any disagreement**.

## Receipt — `.cortex-review-receipt.json` (location + schema live HERE)

**Location:** the cycle folder (`TARGET_DIR`) in cycle-tail mode; the CWD in standalone/read-only modes. **A second PR of the same cycle** (a follow-up PR the cycle opened after its first, e.g. an IaC reconciliation — the canonical receipt already names another PR) is reviewed with `cortex:review pr:<n> folder:<cycle>` in standalone-draft mode, and its receipt lives at `<cycle>/.cortex-review-receipts/<owner>__<repo>__<n>.json` (owner and repo as in `repo`, `/` → `__`). The canonical `.cortex-review-receipt.json` keeps the cycle's first PR and is never overwritten by another PR's review. A follow-up PR is never reviewed lead-only or recorded in an improvised sidecar: it gets the same matrix, debate and cap as any PR. Its receipt records `worktree`, the checkout it was reviewed from, because the exec receipt's `worktree` names only the first one.

## Preflight (before the first round)

1. `gh pr view <num> --json isDraft,state,headRefName,headRefOid,url` — record the baseline in the receipt, and `headRefOid` as the receipt's `head` (re-read and rewrite `head` after every push of a fix round), and the absolute path of the worktree the PR's branch is checked out in as `worktree`. Ready PR → read-only mode. Closed/merged → abort.
2. **Branch protection — query BOTH surfaces**: repo rulesets (`gh api repos/{owner}/{repo}/rules/branches/{base}`) AND classic protection (`gh api repos/{owner}/{repo}/branches/{base}/protection` — tolerate 404, but note it is ambiguous: no protection OR the token lacks admin read; when detection is inconclusive, state the caveat in the delivery comment instead of assuming none). If required status checks exist on either, the loop can never satisfy them (no-CI design) — plan to finish with the delivery comment but **refuse the `gh pr ready` flip**: terminal state `draft + converged-blocked-by-checks`, delivery comment says exactly that, human readies/merges manually.
3. **Unpushed local work on the head branch** (standalone-draft mode): `git log origin/<head>..<head>` — local commits missing from the remote mean the PR diff is stale. Push them first (fast-forward only; a rejected push → stop and hand back). Never review a stale diff, never flip ready over unshipped commits.
4. **Diff profile** (drives the matrix): `gh pr diff <num> --name-only` → classify every changed file into exactly one class — **doc** (`.md`/docs) · **test** (`*.test.*`, `*.spec.*`, `*_test.go`, `test_*.py`/`*_test.py`, `conftest.py`, or any file under `__tests__/`, `__mocks__/`, `test/`, `tests/`, `e2e/`, `fixtures/` dirs; test-runner *config* like `jest.config.*`/`pytest.ini` is NOT a test file — it shapes how every suite runs) · **UI** (`.tsx .jsx .vue .svelte .css .scss .html`, or files under `components/`/`pages/`/`views/` dirs) · **production code** (everything else). Profiles: **markdown-dominant** (>50% of changed files are doc), **frontend-dominant** (>50% are UI), **code** (everything else). Profile thresholds and file classes are defined HERE only — matrix rows reference them by name. Fetch the diff itself for the reviewers.

   **Gate scoping rule (load-bearing):** the conditional code-shaped rows — `security-reviewer`, `type-design-analyzer`, `silent-failure-hunter`, `code-simplifier` — evaluate their gates against **production-code files only**. Test files are `pr-test-analyzer`'s lens, never a trigger for the code-shaped rows: on test scaffolding those lenses produce cost, not signal (a try/catch inside a test is the test *exercising* an error path, not the code *swallowing* one; a helper interface local to a test file is scaffolding, not API surface). Consequence: a **tests-only diff** (every non-doc changed file is a test file) fans out exactly `code-reviewer` + `pr-test-analyzer` (+ `advisor` when reachable) — nothing else.

   **Design-system probe** (drives the `design-system-reviewer` row): when the diff touches ≥1 UI file (the same UI file set above, **excluding `.md`/doc files regardless of directory** — a `components/README.md` is not a UI file; any count, not just frontend-dominant), probe the checked-out worktree for a design system. **Detection requires at least one STRUCTURAL marker**: a `.storybook/` directory · design-token/theme files actually defining tokens (`tokens.(json|js|ts|css)`, `theme.*`, a CSS custom-properties file with multiple custom properties) · an internal component-library dir (`components/ui/`, `packages/ui/`, `src/design-system/` or similar) · a tailwind/panda/vanilla-extract config carrying an extended custom theme. Repo docs (CLAUDE.md/README) referencing a design system or component library are **corroborating evidence only, never sufficient alone** — a lone generic `theme.css` or a doc mention without structure is NOT detection. Record `"design_system": {"detected": <bool>, "evidence": ["<paths>"]}` in the receipt's `preflight` block. No UI files in the diff → skip the probe and record `{"detected": false, "evidence": []}`.
5. **Intent context**: locate the cycle's `PLAN.md`/`EXEC.md` when running as a cycle tail (TARGET_DIR is known) or when the PR body cites them. Extract the excerpts reviewers get: Objective, Approach, Scope (In/Out), Verified facts. Also extract the cycle's recorded operator answers (a `resolved by user` entry in EXP.md's Known or in PLAN.md): each is declared intent for what it asked, and the lead's own pick is not. Standalone with no artifacts → reviewers run without intent context and the debate's intent-dismissal lane is disabled (nothing to cite).

6. **Test-run probe** — skip unconditionally on markdown-ONLY diffs (the exact same skip rule as `pr-test-analyzer`, so whenever that reviewer spawns for a code minority, a probe result exists for it); otherwise run the repo's own test suite so objective failures reach dedup as seeded findings instead of waiting on CI timing.

   - **Reuse before running.** When the **latest** `suite_runs[]` entry in the cycle's `.cortex-exec-receipt.json` for the PR's `head` and the exact detected runner command is `passed` with `clean: true`, that is the probe's result: record it in `test_run` with `reused_from: "<its at>"` and do not run the suite again. A failed, dirty or filtered run is never reused as a pass.
   - **Run in parallel with the fan-out, never before it.** Start the suite in the background (`run_in_background`) in the same message as the reviewer spawns, under the shipped timebox (`python3 <PLUGIN_ROOT>/scripts/cortex_timebox.py 600 -- <runner>`: a background task has no tool timeout, macOS has no `timeout`, and the script stops the runner's whole process group, so a hung child of `npm test` or `make test` is never left behind). Write `test_run: {"status": "running", "output": "<file>", "task": "<the host's background task id>"}` to the receipt when it starts. On resume, reconcile that run before any other:
     - its output ends with `cortex_timebox: exit <code>` → it finished: take that code and its summary line (no summary line → never `passed`);
     - no exit line, and `task` still running for the host, or the output's `cortex_timebox: pid <n>` alive and still the timebox (`ps -o command= -p <n>` names `cortex_timebox.py`) → it is still going: wait for it, never start a second suite;
     - no exit line, the task gone and that pid gone (or never written) → it died unfinished: run it again.

     `pr-test-analyzer` gets the reused result when there is one; otherwise it gets "the suite runs in parallel; judge adequacy statically, and red tests reach dedup as findings". When the run ends, its failures join dedup as seeded findings. Dedup waits for it, so the debate and the fix batch never start without it. Append the run to `suite_runs[]` (`by: review`) when the cycle has an exec receipt.

   - **Detect the runner from repo markers** in the PR's checked-out worktree, first match wins: `package.json` with a real `scripts.test` (not the npm placeholder) → `npm test` (pnpm/yarn per lockfile) · pytest config (`pyproject.toml [tool.pytest]`, `pytest.ini`, `setup.cfg`, `tox.ini`) or a `tests/` dir with `test_*.py` → `pytest -x -q` · `go.mod` → `go test ./...` · `Cargo.toml` → `cargo test` · a `Makefile` `test` target → `make test`. No match → record `no-runner` and proceed.
   - **Run timeboxed** — 10 min hard cap through the timebox above, non-interactive, from the worktree root. Capture pass/fail, failing test identifiers, and the summary line. Exit `124` → record `timeout`, treat as inconclusive (not a failure finding). Exit `127` → record `env-blocked (runner not installed)`. A run whose output has no summary line is never `passed`, whatever its exit code.
   - **Coverage only when the repo already configures it** (pytest-cov/coverage config, jest `coverage` config, a `-cover` flag in the Makefile). Never introduce coverage tooling the repo doesn't use; report the number as context for `pr-test-analyzer` — never invent a threshold.
   - **Outcomes.** All pass → record in the receipt (and, when the run's result is known before the fan-out, e.g. reused, hand the summary and any coverage to `pr-test-analyzer` as context). Failures → each failing test becomes a **seeded finding** entering dedup under the pinned schema: severity `high`, category `tests`, file/line from the failure output, description quoting the assertion/error. Seeded findings are objective — a PLAN.md citation can never dismiss a red test, and they are **exempt from the debate** (nothing to contest — no defender spawn despite their `high` severity): they go straight to the fix batch. `no-runner` / no tests found → record it and proceed; `pr-test-analyzer` still judges adequacy statically — this is signal for it, not a loop failure.
   - **Safety bound.** The suite executes the repo's own code in the already-checked-out worktree — the same trust boundary as the fix rounds. Never run suites that need external credentials or live infra; a suite erroring on missing env → record `env-blocked (<detail>)`, not a failure finding.

## Reviewer matrix — conditional fan-out, never all-always

Spawn only what the diff profile calls for, all in ONE message (parallel), each as a plain unnamed `Agent(description, subagent_type, model, prompt)` — **`model` is pinned per row below, never inherited from the session**:

| Reviewer | Spawn when | model | agentType |
|---|---|---|---|
| `code-reviewer` | always | `opus` | `pr-review-toolkit:code-reviewer` |
| `advisor` | always — **when `advisor()` is reachable in the session**; silently skipped otherwise (the specialized fan-out is the primary gate) | — (non-spawn) | `advisor()` — the **proportionality lens**: the lead writes the review-row agenda of `<PLUGIN_ROOT>/skills/exec/references/advisor-agenda.md` right before the call. It asks what in the diff is over-engineering by that file's definition, what the acceptance criteria still miss, and which other findings cost more to fix than the risk they carry (within the severity floor) |
| `docs-reviewer` | diff is markdown-dominant (preflight §4 profile) | `sonnet` | `general-purpose` + prompt grounded in the target repo's CLAUDE.md when present (conventions, frontmatter consistency, cross-file contracts, broken internal references); **no CLAUDE.md → ground in generic doc quality** (accuracy vs the diff, internal consistency, broken references) and skip convention checks |
| `pr-test-analyzer` | new/changed logic or test files in the diff | `sonnet` | `pr-review-toolkit:pr-test-analyzer` — its prompt additionally includes the preflight test-run status (§6) known at spawn time: the run summary (runner, pass/fail, failures, coverage when the repo configures it) when a reused run supplies it; "the suite runs in parallel; judge adequacy statically, red tests reach dedup as findings" while it runs; else the recorded state (`no-runner`/`no-tests`/`env-blocked`/`timeout`) with instruction to judge adequacy statically. Never wait for the suite to spawn it. |
| `silent-failure-hunter` | **production code** in the diff touches error handling / catch / fallback paths (gate scoping rule, preflight §4 — a test asserting an error path is `pr-test-analyzer`'s lens, not a trigger) | `opus` | `pr-review-toolkit:silent-failure-hunter` |
| `type-design-analyzer` | new types/schemas/interfaces added **in production code** (gate scoping rule — types local to test files are scaffolding, not reviewed type surface) | `opus` | `pr-review-toolkit:type-design-analyzer` |
| `code-simplifier` | large diff (>400 changed lines of **production code** — gate scoping rule; verbose tests don't buy this pass) | `opus` | `pr-review-toolkit:code-simplifier` |
| `security-reviewer` | changed **production code** that is security-relevant (gate scoping rule — still fires on a production-code minority inside a markdown-dominant diff; a tests-only diff spawns no security row — test scaffolding is not attack surface, and a real credential hardcoded in a test still rides `code-reviewer`). **It fails closed:** it runs unless every production-code change is plainly none of these: input handling or validation, authn/authz, queries or persistence, secrets or config, an external call (HTTP, SDK, queue), deserialization, file or path handling, IaC/permissions, or a dependency manifest. The skips are things like a rename, a constant, copy text, styling, or a refactor with no behavior change. When in doubt, it runs. | `opus` | `general-purpose` + OWASP-grounded prompt: injection (SQL/command/template), broken authn/authz, hardcoded secrets or exposed config, SSRF, unsafe deserialization, path traversal, vulnerable/malicious dependency changes, crypto misuse. Report only what the diff evidences — no speculative hardening checklists. |
| `frontend-ux-reviewer` | diff is frontend-dominant (preflight §4 profile) | `opus` | `general-purpose` + UX lens prompt: accessibility (semantic markup, focus management, contrast, ARIA), UI states (loading/error/empty — a genuinely broken failure state, e.g. blank render on fetch error, is category `silent-failure`), responsiveness. Design-system conformity is NOT this lens — it belongs exclusively to `design-system-reviewer`; **when the preflight probe detected NO design system — or the DS row retracted detection as `no-real-ds` (effective from the round the retraction is recorded) — generic visual/pattern consistency within the diff returns to this lens** (the two lenses are mutually exclusive by the probe's outcome; within frontend-dominant diffs there is no coverage hole. Accepted residual, stated: a non-frontend-dominant diff with UI files and no detected DS spawns neither lens — generic visual consistency there rides `code-reviewer` only). A11y violations that block access (keyboard traps, screen-reader-invisible content, unreachable actions) → category `bug`; the rest → category `ux`. |
| `design-system-reviewer` | diff touches ≥1 UI file (preflight §4 file set — deliberately NOT gated on frontend-dominant: a single off-DS component in a mixed diff is exactly the drift this row exists to catch) AND the preflight design-system probe detected one | `opus` | `general-purpose` + DS-conformance prompt, armed with the probe's evidence paths: check every changed UI element (components, styles, tokens, spacing, colors, typography) against the design system. Each deviation → category `design-system` with a `ds_case`: `ds-violation` (a DS equivalent exists and was not used), `ds-gap` (no DS equivalent — a new pattern the DS lacks), `ds-intent` (the intent excerpts explicitly request the off-DS pattern), `ds-sibling` (a difference in layout or states from the closest sibling, from the comparison below). Severity: `ds-violation` medium, high when it visibly forks an established pattern; `ds-gap`/`ds-intent` medium. **Sibling comparison:** for each NEW screen in the diff (a UI file the diff adds that renders a whole screen or route; a thin route file wrapping a new screen component counts as one screen), compare layout and states (loading, empty, error, refetch) against its sibling: the closest existing screen of the same type (list to list, detail to detail, form to form) at the PR's merge base, reading files outside the diff for this. A state or element the new screen has and the sibling lacks is not a reportable difference, nor is one where the sibling itself departs from the design system on a layout or state the new screen also has. Severity of an undeclared difference: medium; high only when the new screen moves a structural element out of the sibling's layout or omits a state the sibling has; a declared difference is medium. A change of component or token that leaves layout and states unchanged is the DS check's alone and is never a `ds-sibling`. Each difference is `ds-sibling`: declared when an exact PLAN.md line or a recorded operator answer names that layout or state; undeclared otherwise, and the finding names the missing record; no comparable screen → no finding. The sibling is a read-only reference: findings land only on the diff and defects in the sibling are never reported. Report only what the diff evidences — no DS-wide audits, the sibling comparison included. If the probe's evidence turns out NOT to be a real design system, return zero findings stating exactly that — the lead records it in the receipt as `design_system.reviewer_verdict: "no-real-ds"` (`detected` stays as the probe reported; the verdict IS the retraction — not an infra failure, no fallback). **Lens ownership: DS conformity is reported by this row alone**, so the fan-out never produces duplicate reviews of the same deviation. |

**Profile: small** (PLAN.md's `> Profile: small` header, cycle-tail mode or a run from the cycle folder). The preflight re-checks the criteria (`<PLUGIN_ROOT>/skills/plan/SKILL.md` § "Profile: small") against the **whole** PR diff: `gh pr diff <num>`, counting every changed line outside the test class, and scanning for the excluded areas. It records `preflight.profile: {"plan": "small", "effective": "small | standard", "broken": "<criterion or null>"}`. When any criterion breaks, the standard matrix runs on the whole diff. When they hold, every row keeps its own gate, except `type-design-analyzer` and `code-simplifier`: those are skipped, `gate: "skipped: small profile (PLAN.md header)"`. The test-run probe still runs.

**A small cycle's re-review after a scope addition** reviews the delta from the head the previous receipt recorded. Read that head before preflight step 1 rewrites `head`, and record it as `delta_base`. The whole diff is reviewed instead, with the standard matrix when the criteria no longer hold, in two cases: the whole diff no longer meets the criteria, or the previous review did not converge (`terminal: draft-needs-human`). A delta review **carries forward** every `deferred:*` row of the previous receipt into the new receipt and the delivery comment: a blocking row stays blocking, and a `deferred:risk` that bears on an acceptance criterion keeps its row.

**Every row records its `gate`** in the receipt's `reviewers` entry: why it ran (the matched rule and the file that matched), or, for a conditional row that did not run, why it was skipped. A gate reason that cites no file, for a conditional row that ran, is malformed; a skip names the rule that did not match. The receipt then shows that every spawn was earned, and that every skip was deliberate.

**The `model` pin is authoritative and overrides the agent definition's own frontmatter** (several `pr-review-toolkit` agents declare `model: inherit` or their own tier — the call-site value wins). Use the bare tier aliases `"opus"` / `"sonnet"`, which always resolve to the latest of that tier — never a pinned version ID. `docs-reviewer` and `pr-test-analyzer` run `sonnet` because they are breadth passes over prose and coverage adequacy where the row's prompt carries the rigor; every other row runs `opus` because correctness, security, and design judgment are exactly where the reasoning tier is the differentiator. **Reasoning effort is not a per-spawn knob** — the `Agent` tool exposes no `effort` argument, so reviewers inherit the session's `effortLevel` (`high` by default in every `/cortex:init` cycle). Do not attempt to set it in the prompt.

**Markdown-only diffs skip `type-design-analyzer` and `pr-test-analyzer` unconditionally** — they are code-shaped and produce noise on docs. (`security-reviewer` needs no skip entry — its gate reads production-code files and a markdown-only diff has none; `frontend-ux-reviewer` needs none either — a markdown-only diff can never be frontend-dominant; `design-system-reviewer` likewise — a markdown-only diff touches no UI files, so its gate never fires.)

**Tests-only diffs collapse the fan-out to `code-reviewer` + `pr-test-analyzer` (+ `advisor`)** — this is the gate scoping rule (preflight §4) doing its job, not a special case: every other conditional row's gate reads production code and a tests-only diff has none. Spawning the full matrix on a test-heavy PR is the canonical over-spawn failure — slow, costly, and each extra lens reviews scaffolding it was never designed for. The test-run probe (§6) still runs (tests are code, not markdown), so red tests still seed findings.

**`security-reviewer`, `frontend-ux-reviewer`, and `design-system-reviewer` are `general-purpose` by design** — no pr-review-toolkit agent exists for these lenses. They are first-class matrix rows, not fallbacks: never recorded in `spawn_fallbacks`, and they carry the same pinned schema and isolation bound as every other spawn. An infra error on these rows follows the same retry-once rule; a second error → the lens is skipped for the run and recorded in the receipt's `reviewers` list as `failed (infra)` — there is no further fallback and nothing enters `spawn_fallbacks`.

**The `advisor` row is the one non-spawn entry.** `advisor()` is a direct in-session call, not an `Agent(...)` spawn: it takes no diff-scoped prompt, sits outside the fallback contract (unreachable → silently skipped, recorded in the receipt's `reviewers` list), and is **never re-run in fix rounds**. Its findings are normalized into the pinned schema by the lead before dedup. **Lead-only call site**: the lead calls it exactly once per review as this matrix row — plus at most one batched triage call (all out-of-scope questions in one `advisor()`, § "Out-of-scope suggestions"), at most one sizing call per fix round (§ "Fix loop") and at most one grant call per review (§ "Advisor round") — reviewer and fix-author subagents never call it (see the isolation bound in the prompt requirements below).

Every reviewer prompt is self-contained and MUST include:
- The PR diff (or the file subset relevant to that reviewer).
- The intent excerpts of preflight §5 (PLAN.md and the recorded operator answers when present) — labelled "declared intent, for context".
- The **pinned finding schema** — findings MUST come back as a list of: `severity` (high|medium|low) · `file` · `line` · `description` · `category` (bug | silent-failure | security | design | scope | simplification | tests | docs | ux | design-system). `design-system` findings additionally carry `ds_case` (ds-violation | ds-gap | ds-intent | ds-sibling — defined in the `design-system-reviewer` row). Free-text findings are rejected at dedup. **A finding states a problem, never a question**: a reviewer wanting a decision reports the fact that makes it needed ("X is ambiguous: code does A at `file:line`, spec implies B"), not "decide X"; pure refactor/style/naming preferences are reported as `category: simplification` with severity `low` — in scope they follow the normal verdicts (`code-simplifier`'s row exists for that); out of scope they are opinions the lead judges (§ "Out-of-scope suggestions").
- The **isolation bound**: *"Do NOT call `advisor()` and do NOT spawn your own sub-reviewers to validate or filter your findings — return them raw, including the uncertain ones. Independence is the point: the advisor is already a separate voice in the fan-out, and the lead's dedup + debate steps do the filtering."* Reviewers pre-filtering through a shared advisor correlate the voices (everyone converges to the advisor's bias before the debate), double-count the advisor's opinion, and burn a full advisor call per reviewer per round — each one bypassing the never-re-run-in-fix-rounds cap that binds the lead's single call.
- The bound: *"If you get stuck or a tool errors, return what you have and STOP — don't keep retrying."*
- Reports in English.

**Fallback contract** (mirrors cortex:exec's spawn contract): a spawn that returns an infra **error** is retried once; a second error → fall back to `general-purpose` with an inline prompt replicating that reviewer's specialty **and the same pinned schema** (a free-text fallback silently corrupts dedup/debate) **and the failed row's pinned `model`** — a `pr-test-analyzer` fallback stays `sonnet`, a `silent-failure-hunter` fallback stays `opus`. Only the agentType degrades; the tier never does, otherwise the pin evaporates in exactly the case the fallback exists for. Every fallback is recorded in the receipt's `spawn_fallbacks`. `pr-review-toolkit` is an optional dependency by design — absence is a supported path, not a failure.

## Dedup (lead, no spawn)

Merge findings by (file, line-range, category). Keep the highest severity on collision. A `ds-sibling` finding never merges with a finding of another `ds_case`, and two `ds-sibling` findings merge only when they describe the same difference. **A11y promotion happens here, before any dismissal lane**: findings meeting the blocks-access bar (defined in the `frontend-ux-reviewer` row) are promoted `ux` → `bug` prior to merging. **DS lens ownership is enforced here too — but ONLY when the preflight probe detected a design system AND the DS row has not retracted it (`reviewer_verdict: no-real-ds`)**: a DS-conformance-shaped finding arriving from any other reviewer (e.g. a `ux` or `design` finding whose substance is "doesn't use the design system's component/token", or a sibling state or layout difference reported by another row on a new screen, within the limits of that row's sibling comparison) is re-categorized to `design-system` (the lead assigns its `ds_case` grounded in the probe's evidence; a sibling state or layout difference takes `ds-sibling`) and merged — one deviation is never reviewed twice under two labels. With no detected DS, such a finding keeps its original category and lane — the lead never invents a `ds_case` without probe evidence. Auto-dismiss findings that presuppose a compiled/typed language when the diff is markdown-only (record as `dismissed (not applicable)`).

## Debate — economical, adversarial, bounded

Only two classes of findings earn a debate spawn; everything else resolves by lead judgment:

- **high severity** findings, always — EXCEPT suite-seeded `tests` findings (preflight §6 or a fix-loop re-run's regressions), which are objective (a red test is not an opinion): no defender spawn, straight to the fix batch.
- **contested** findings — the lead, reading the finding against the diff and intent excerpts, considers it plausibly wrong.

Per debated finding, spawn ONE `defender` (`general-purpose`) armed with the diff hunk + the preflight §5 intent excerpts (PLAN.md/EXEC.md and the recorded operator answers), prompted to argue whether the finding misreads the code or contradicts documented intent. The lead judges. The same isolation bound applies: the defender argues from the hunk and excerpts only — no `advisor()` calls, no sub-spawns.

**Design-system triage lane (category `design-system` — resolves by `ds_case`, never by the generic dismissal lane):**

- `ds-violation` → `confirmed` → fix batch: replace the hand-rolled element with the DS component/token. Normal debate rules apply when contested — a defender may argue the DS equivalent doesn't actually cover the case; sustained, the finding is reclassified `ds-gap` (below), not dismissed. **A contested `ds-violation` that ties also reclassifies to `ds-gap`** — the generic `dismissed (unproven)` tie rule does not apply to a `ds-violation` (the `ds-gap` row is the cheap, silence-free resolution; the DS owner adjudicates).
- `ds-gap` → never fixed, never dropped: the new pattern ships, and the DS must catch up — a non-blocking `issue-candidate` row in the delivery comment, titled `DS gap: <pattern>`.
- `ds-intent` → **carve-out from the anti-intent-laundering rules below: a citation from the intent excerpts (§5) RECLASSIFIES a deviation as intended — it never silently dismisses it.** The code stays (operator intent is respected), but the deviation is tracked: a non-blocking `issue-candidate` row in the delivery comment, titled `Operator-requested DS deviation: <pattern> — incorporate into the DS or revert`, and surfaced in its `⚠ Design system` line. The loop may still converge and flip ready — incorporate-vs-revert is the operator's call at the merge gate.
- `ds-sibling` → a difference in layout or states from the closest sibling (the `design-system-reviewer` row's sibling comparison), a separate fact from any component or token finding on the same element. **Undeclared** → `confirmed`, and the finding names the missing record. Before the fix batch the lead checks the recorded operator answers in the intent excerpts (§5). One that asked for this difference, quoted in the rationale, resolves the finding as Declared. None → fix batch: match the sibling's layout or states, adding a missing state with the design-system component where one exists; a sustained defense is `dismissed (disproven)`, a tie follows the generic tie rule, and it never reclassifies to `ds-gap`. **Declared** (backed by an exact PLAN.md line naming that layout or state, or by a recorded operator answer found as above) was decided by a recorded line: verdict `out-of-scope`, outcome `answered:<the line>`, no `triage`, listed in the delivery comment's `⚠ Design system` line.

Receipt bookkeeping: `ds-gap` and `ds-intent` findings record verdict `out-of-scope` with outcome `issue-candidate` (`triage: unquestionable`) — mechanical reuse of the out-of-scope verdict, NOT a scope judgment (a `ds-intent` deviation is inside the PLAN's scope by construction); `ds-violation` and an undeclared `ds-sibling` follow the normal `confirmed`/`dismissed` vocabulary (where "dismissed" can only mean the deviation was disproven or, for a `ds-sibling`, that a tie went `dismissed (unproven)`; never intent-laundered), and a declared `ds-sibling` records the row its bullet names. **Read-only mode: ALL `design-system` findings — including confirmed `ds-violation`s, which cannot be fixed there — degrade to `issue-candidate` rows in the delivery comment, except a declared `ds-sibling`, which keeps its `answered:` row because it needs no fix.**

Rationale (load-bearing): the design system / Storybook must never rot into a mix of divergent patterns. Every off-DS element that ships is either fixed in the PR or leaves a row in the delivery comment pointing at the DS — **silence is the only forbidden outcome.**

**Anti-intent-laundering rules (load-bearing):**
- A PLAN.md citation can dismiss **only** `scope` / `design` / `ux` category findings — `design-system` findings are excluded: intent reclassifies them to `ds-intent`, which still leaves a row in the delivery comment, except a `ds-sibling`, which a citation can only declare (triage lane above). Findings in `bug`, `silent-failure`, or `security` categories — and suite-seeded `tests` findings (preflight §6 or fix-loop re-run regressions) — can **never** be dismissed by intent alone — intent doesn't fix a crash or a red test. (A11y findings that meet the blocks-access bar defined in the `frontend-ux-reviewer` row belong in `bug`: the lead promotes them from `ux` to `bug` at dedup, before any dismissal lane — the reviewer's label is not the last word.)
- A dismissal-by-intent (and a `ds-intent` reclassification, and a declared `ds-sibling`) requires the **exact quoted line from the intent excerpts (§5)** plus a causal explanation of why that line makes the finding wrong (or the deviation intended) — a topical gesture at the document is not a dismissal.
- **Tie → no fix** (burden of proof is on the finding): low/medium ties land in `dismissed (unproven)`; **high-severity ties land in `deferred to human`** (outcome `deferred:tie` — non-blocking) — never silently dropped.
- **Proportionality questions cost, never existence.** When the proportionality lens says a finding costs more to fix than the risk it carries, the finding goes to the round's sizing call (§ "Fix loop"). It is never dismissed on that ground. A floor-area finding, or a `high` from any lens, is sized only to choose its fix or a check, never to defer it (`advisor-agenda.md` guardrail 1).

Verdicts per finding: `confirmed` (→ fix batch) · `dismissed (reason)` · `deferred to human` · `out-of-scope` (→ triage per § "Out-of-scope suggestions": `answered` / `judged` / `issue-candidate`; operator-taste questions, questions the triage cannot answer and `high` classification ties leave the lane as `deferred to human`). All verdicts + rationale go in the receipt. **`deferred to human` has four kinds, recorded in the outcome:**
- `deferred:tie` (a debate or classification tie) and `deferred:taste:<lead reading>` (an operator-taste question, or one the triage cannot answer) are **non-blocking**. They render as rows for the human at the merge gate, and the loop may still converge.
- `deferred:risk:<sizing>` is **non-blocking** too. It is a real finding whose fix the round's sizing call (§ "Fix loop") judged not worth its cost, for one of two reasons:
  - the precondition is unlikely by a **cited fact**, never by a guess;
  - the available fix is partial or adds a new failure mode.

  The row carries the sizing. It never applies, without the operator, to a finding in a floor area or to a `high` from any lens, suite-seeded failures included (`advisor-agenda.md` guardrail 1). For those, the sizing may only choose a fix or a check. A `high` or floor-area finding the fix rounds do not close reaches the cap as `deferred:cap:<high | floor:<area>>`, and becomes `deferred:risk` only by the operator's own `Accept residual risk`. When the residual bears on an acceptance criterion, the row names the criterion. Accepting it is then the operator's call at the merge gate.
- `deferred:cap:<why>` (items the cap or the oscillation guard left, of the blocking kinds in § "Fix loop") **blocks convergence**: the PR stays draft, header `needs human`.

The cap's other leftovers are not deferred to a human: they leave as `deferred:followup` (a non-blocking row in the delivery comment).

## Fix loop — lead-committed, capped, oscillation-guarded

- **All confirmed in-scope findings are applied, by fix-authors in parallel grouped by file footprint.** The lead lists the files each finding's fix changes and groups the findings: two findings whose file sets overlap, directly or through a third finding, are in one group, so no two groups share a file.
  - **Before spawning, the lead records `git status --porcelain` as the round's baseline.** Whatever is already listed there — a standalone run's `evidence/` and receipt, say — is never a fix-author's change.
  - **One fix-author per group, all spawned in ONE message**, the way `cortex:exec` spawns the owners of a parallelizable phase (`<PLUGIN_ROOT>/skills/exec/SKILL.md` § "Coordination model"): a plain unnamed `Agent(description, subagent_type: "general-purpose", model: "opus", prompt)`. A group whose fix is one edit the lead can hold, the lead applies itself, with no spawn.
  - **A spawn that returns an infra error** is retried once. A second error → the lead applies that group inline, recorded in `spawn_fallbacks` (`{"agent": "fix-author:<the group's first file>", "reason": "spawn-infra-error", "resolution": "inline"}`). When the lead cannot apply it either, the resolution is `failed (infra)`, and the group's findings stay unfixed into the cap classification.
  - **The prompt is self-contained:** the pinned worktree path; the group's findings in the pinned schema, with their hunks; the intent excerpts (preflight §5); the group's files, the only files it may change (a fix that needs another file stops and reports which); the minimal-fix rule at the end of this section; *"do not commit — return the changed files and one line per finding"*; and the reviewer prompts' isolation and stuck bounds.
  - **A finding reported as needing a file outside its group** is applied by the lead after the parallel groups land, in its own commit, in the same round, before the gates run.
  - **Commits are the lead's, one per group** (`git add -- <the group's files>`), per `<PLUGIN_ROOT>/skills/commit/references/commit-conventions.md` (subagents never commit). The lead verifies each commit landed via `git log` (exit codes lie less than prose).
  - **A stray path is a stop.** A path `git status --porcelain` lists against the round's baseline that is outside every group's files stops the round before the gates: the lead reverts it, or folds it into a group as that group's change, and records which in the round's `strays`. If a commit-time hook (e.g. the security-guidance plugin) fires: fold its output into the current round's findings, fix, retry the commit — **never `--no-verify`**.
  - **The gates run once per round**, after every group has landed: one push, one suite re-run, one re-run of the affected reviewers (the bullets below).
- Push, then re-run **only the reviewers whose flagged files were touched by the fixes** — never broadcast to the full matrix. Accepted risk (stated): a fix touching a file no reviewer flagged goes unre-reviewed within the cap.
- **Re-run the test suite after every fix batch**: same runner and timebox as preflight §6, started in the background together with the affected reviewers' re-run, and appended to `suite_runs[]` like the preflight run. **The round's verdict waits for it**: no next round, convergence, delivery comment or ready flip before its result is in; skipped whenever preflight did NOT produce an actual run result (any of `no-runner`, `no-tests`, `env-blocked`, `timeout`, or the markdown-only skip). New failures = regression findings (severity `high`, category `tests`) that count toward the oscillation guard — fixes breaking tests is exactly the "findings grow" signal that stops the loop. Record the outcome in the round's receipt entry (`tests_after`; a re-run that itself times out or hits env-block records that state, not a failure).
- **Sizing call, at most one per round, before the batch.** It is required when the round's confirmed set holds a concurrency, ordering, retry or edge-case finding, or a finding whose evident fix is partial. The lead writes the sizing agenda of `<PLUGIN_ROOT>/skills/exec/references/advisor-agenda.md` and makes one `advisor()` call that covers all such findings, sizing each on its own: is the precondition realistic (cite the fact)? what is the impact? is the fix partial? does it add a new failure mode? With `advisor()` unreachable the call is skipped, the round's `sizing` records `unsized: advisor unreachable`, and each of those findings takes its fix.
  - Per finding the result is a fix, `deferred:risk:<sizing>` (within guardrails 1–2), or a check the batch runs first when the deciding fact is unknown. Unknown is not unlikely.
  - The result goes in the round's `sizing`.
  - This call and the advisor round's grant call (§ "Advisor round") are the two exceptions to "the advisor is never re-run in fix rounds". That rule binds the matrix row, not these bounded calls.
- **The right fix lives in a shared component outside the change.** When a confirmed finding's real fix belongs to a shared component the change neither touches nor makes worse, the loop does not build a partial wrapper around it:
  - it records `deferred:risk:<sizing; shared fix in <component>>`;
  - its delivery-comment row names the component's defect, for the human to carry forward.

  This is not available when the change itself introduced the defect or made it worse: then the defect is in scope and gets fixed here. Nor for a floor-area or `high` finding: the row still names the component, but the finding stays blocking (`deferred:cap:<floor:<area> | high>`) for the operator to decide.
- **Hard cap: 2 fix rounds.** Not advisory. One more runs only by the advisor's grant (§ "Advisor round") or a `Review round` answer. Track the findings-diff between rounds in the receipt.
  - **Round 2.** It may address findings that round 1's re-run surfaced **only when the set is convergent**: strictly fewer findings than the previous round, and none of higher severity.
  - **Two stops.** Either one ends the loop at once and sends the remaining items to the cap classification below:
    - *Oscillation by count:* the re-run's findings **grow in count or severity**, so fixes are spawning worse findings.
    - *Oscillation by area:* a round's fixes change a `fix_areas` entry again to address what the previous round's fix in that same area caused. The approach in that area needs reassessing, not a third patch.

    A stop is never `needs human` by itself: the cap classification decides. When every item it leaves is non-blocking, the loop converges with the follow-ups listed in the delivery comment.
  - **The cap is the cap.** After round 2's re-run, anything remaining goes to the cap classification below.
- **Cap classification: what still blocks.** Each confirmed finding left by the cap or an oscillation stop goes one of two ways.
  - It **blocks** as `deferred:cap:<why>` when any of these holds:
    - `high`: its severity is high;
    - `floor:<area>`: it is in a floor area (tenant isolation, authn/authz, data integrity, a financial or limit rule, security — `advisor-agenda.md` guardrail 1);
    - `regression:<sha>`: **this loop introduced it and its severity is `medium` or `high`**; `<sha>` is the commit its `caused_by` names, or, when that is `unknown`, the `fixed:<sha>` its call path traces to, or, when nothing traces, the round's last commit (below). It sits in a hunk a `fixed:<sha>` commit of this loop changed; or it is a suite regression after a fix batch; or a re-run reported it for the first time and its cause traces to a `fixed:<sha>` change (cite the call path). A finding first reported by a re-run is presumed this loop's unless the lead shows the same defect at the head the round started from, before its fixes.
  - **`caused_by` keeps the cause.** Every finding this loop introduced, by the same test, records `caused_by: "<sha>"`, whatever its severity. It is one sha: the most recent commit of this loop that changed the finding's hunk, read against the start head of the round that addresses it (every earlier commit landed): the first sha `git log -L <a>,<b>:<file> <that head>` lists among the rounds' `fixed`. That covers a commit outside every group and a hunk only round 1 changed. When that log holds no loop commit, the finding records `caused_by: "unknown"`. It still blocks as `regression:<sha>` when its call path traces to a `fixed:<sha>` change, and `<sha>` is then that traced commit. Any other presumed regression — a suite regression or a finding a re-run reported first — that nothing traces names the round's last commit, and its `rationale` says so: an untraced cause never turns a presumed regression into a follow-up. An `unknown` cause counts toward no `fix_areas` entry in criterion (e). The key stays when a later round fixes the finding (`fixed:<sha2>`) or the cap defers it, so the causal chain survives the outcome rewrite; § "Advisor round" criterion (e) reads it.
  - **Everything else** is listed in the delivery comment. Its outcome is `deferred:followup`: non-blocking. This includes a `low` regression of this loop's own fix outside the floor areas.
  - **A follow-up never waives an acceptance criterion.** A leftover that leaves one of the plan's acceptance criteria unmet (a required empty or error state still missing, say) is listed the same way and does not block the loop's convergence. Its receipt row carries `"ac": "<the criterion, verbatim>"`, and its delivery-comment row says `AC <n> unmet: operator decides`. Convergence is the review's; acceptance is not. An unmet criterion blocks an unconditional acceptance of the outcome, whatever its deferred outcome. Accepting the PR without it is the operator's scoped exception, like a `deferred:risk` row against a criterion.
  - When no blocking leftover remains, the loop **converges**, and its terminal follows § "Ship & ready" as usual. When one remains, the advisor round comes first (§ "Advisor round"). Not granted, the PR stays draft with the `needs human` header.
  - The session may then ask the fixed-shape `Review round` question (§ "Review round").
- Fixes are minimal and targeted: no drive-by refactors, which widen the blast radius that spawns new findings. Over-engineering, as `advisor-agenda.md` defines it, is never a fix.

## Advisor round — the one round the advisor may grant

When the cap classification leaves blocking items, after round 2's re-run or an oscillation stop in round 1 or 2, the loop does not end yet. Before the terminal write, the delivery comment and any `Review round` question, the lead makes **one** `advisor()` call when it is reachable, with the grant agenda of `<PLUGIN_ROOT>/skills/exec/references/advisor-agenda.md`. It happens once per review. A call that cannot reach the advisor is recorded as `advisor_grant: "unreachable"` in the same write as the terminal, so a resume before that write finds no `advisor_grant` and calls again. Once a value is recorded, nothing calls again.

The advisor grants the next round (round 3, after a full cap) only when every criterion below holds. (a) is the lead's own check before the call; the advisor answers (b)–(e), each with a cited fact, and an unknown is not met (guardrail 2).

| # | Criterion | Holds when |
|---|---|---|
| (a) | the call is due | blocking `deferred:cap` items remain, and `advisor_grant` is absent. A round after the first terminal write (a `Review round` grant) or after a granted advisor round finds it set, so the advisor never grants past the round after the stop |
| (b) | concrete fix | every blocking item is sized as a concrete fix inside the plan: the fix is not partial, adds no new failure mode, and adds no scope PLAN.md does not hold |
| (c) | green suite | the last suite result at the head is `passed`. `skipped` counts only when preflight had nothing runnable (`skipped (markdown-only)`, `no-runner`, `no-tests`); a `timeout` or `env-blocked` probe fails it |
| (d) | reversible | no fix has an irreversible step: no migration or data change applied, no deletion outside the worktree, no history rewrite, no call that changes external state |
| (e) | no 3rd oscillation | the round would not be the 3rd causal oscillation in one `fix_areas` entry. A causal oscillation is a round whose fix changes an entry to fix a finding whose `caused_by` commit changed that same entry. Count them over the receipt's rounds and findings, the round asked for included |

**The area stop and (e) count the same oscillations.** One causal oscillation in a `fix_areas` entry stops the automatic loop (§ "Fix loop", the area stop). It does not refuse the advisor round: that round may patch the entry again, and only (e) refuses it there, when it would be the 3rd causal oscillation in that entry.

- **Granted.** The round runs like a `Grant one more round` round: scoped to the blocking items, then the same fix batch, re-run and cap classification. The receipt is still `partial`, so the first terminal write and the delivery comment come after it. Its `rounds[]` entry records `granted_by: "advisor"`, `criteria: ["b", "c", "d", "e"]` and `criteria_reasons` (one line per letter); the receipt records `advisor_grant: "granted"`. The call is that round's sizing call.
- **Not granted, or the advisor unreachable.** The receipt records `advisor_grant: "refused:<letters>"` or `"unreachable"`, and `advisor_grant_detail` keeps the reasons and the per-item sizing. Unreachable, every blocking item's sizing is `unsized: advisor unreachable`, and that is its sizing: no second call follows. The loop ends `draft-needs-human`, and the `Review round` question follows at once, unchanged. That sizing is the sizing the question cites.
- **The advisor only grants.** It never accepts a residual, never stops the PR and never turns an item into `deferred:risk`; the severity floor binds it as in every call. A granted round never changes a blocking item's status: a floor-area or high item it leaves open stays `deferred:cap`. A granted round that still leaves blocking items goes to the `Review round` question, and every round after it is the operator's.

## Review round — the one question the cap may raise

The loop itself never asks. When it ends `draft-needs-human` because of blocking `deferred:cap` items, the cycle's session (`cortex:exec`'s wrap-up, or a standalone run that has an operator) asks the `AskUserQuestion` below, with a fixed shape. It is asked again after each extra round that still ends with blocking items:
- **Header:** exactly `Review round`, on every re-ask too: the round number goes in the question, never the header (AskUserQuestion caps a header at 12 characters). Keep the three labels verbatim, too.
- **Question:** each blocking item with its `<why>`, the sizing from the last round's call (`unsized: advisor unreachable` when the advisor could not be reached), and the criteria the advisor round refused (`advisor_grant`), each by its letter and a reason that names the step. For example: `(c) the last re-run timed out at the head`, `(d) the fix runs a schema migration on a live table`, `(e) a 3rd patch to readRecipient in src/cli/run.ts`. A blocking item with no sizing gets one sizing call first, under the same agenda, and that call counts as the next round's; `unsized: advisor unreachable` is a sizing, and no call follows it.
- **Options:** exactly three labels, each with a one-line description of its consequence:
  - `Grant one more round`: one more fix round scoped to the blocking items only, followed by the same re-run and cap classification;
  - `Accept residual risk`: the blocking items become `deferred:risk:<sizing>` and the loop converges. The severity floor still applies: a floor-area or `high` item is accepted only by the operator;
  - `Stop: needs human`: the PR stays draft.

**What each answer does to the receipt and the comment** (the loop had already written `status: complete`, `terminal: draft-needs-human` and its delivery comment):
- `Grant one more round`: write `status: partial`, `terminal: null`, `completed_at: null` before the round starts (the shape of a loop in flight); append the round; after its re-run and cap classification, write the terminal again and **edit** the same delivery comment (`gh api -X PATCH repos/<owner>/<repo>/issues/comments/<id>`), so the one-comment bound holds.
- `Accept residual risk`: rewrite each blocking item's outcome to `deferred:risk:<sizing; accepted by operator>`. An unsized item writes `deferred:risk:accepted by operator; unsized (advisor unreachable)`: the one `deferred:risk` that cites no fact, because the operator accepted it without one; the loop has converged, so finish § "Ship & ready" (ready flip, or kept draft by scope) and edit the delivery comment.
- `Stop: needs human`: nothing changes.

Do not prototype a fix before asking.

## Out-of-scope suggestions → triage, then delivery-comment rows

A reviewer suggestion that falls outside the PLAN's scope (or outside the PR's evident purpose, in standalone mode) is **never applied as out-of-scope work and never silently dropped**. Despite the prompt requirement that findings state problems, questions and opinions still arrive (reviewers return raw findings by design). The lead triages every out-of-scope finding into exactly one of three classes before it is reported. All of them live only in the delivery comment, and none blocks convergence. **Substance beats wording:** a finding phrased as a suggestion that nonetheless carries an evidenced defect ("consider a null check at `file:line` — it crashes on empty input") is **unquestionable**, never a question — the class tests below are applied to what the finding proves, not to its verbs.

| Class | Test | Lead's move | Outcome |
|---|---|---|---|
| **question** | The finding asks for a decision instead of stating a defect — wording like *decide / whether / consider / argue / measure / which semantics / should we* — AND proves no defect on its own | **Answer it.** The lead's own judgment against the diff, PLAN.md, EXP.md and repo conventions, with the questions folded into **one batched `advisor()` triage call** when the advisor is reachable. | `answered:<one-line answer>` — recorded in the receipt and the delivery comment. A question the triage cannot answer is left to the human: verdict `deferred to human`, outcome `deferred:taste:<lead reading>`, one row in the delivery comment. |
| **opinion** | A preference or alternative with no demonstrated defect — refactor/simplification wishes, naming taste, "could be", "might be cleaner", style — anything a competent engineer could reasonably reject | **Judge it.** Agree or disagree, with a reason. An opinion that turns out to be trivially inside the PR's purpose is **reclassified in-scope** (it was never out of scope) and takes the normal fix loop and its cap, outcome `fixed:<sha>`. | `judged:<reason>` — recorded in the receipt and the delivery comment — or, when reclassified in-scope, verdict `confirmed` + `fixed:<sha>` (the `triage: opinion` key stays for the audit trail). |
| **unquestionable** | A concrete, evidenced fact: `file:line` + what breaks / what is missing + against which stated contract (a spec, a type, a documented invariant, a failing input) — verifiable by reading the code, **no taste judgment needed**, and phrased as an executable directive. Severity is irrelevant: a `low` fact qualifies, a `high` opinion does not. | **Report it**: one row stating the problem, its `file:line` evidence at the PR's head, and the expected behavior. | `issue-candidate` — a non-blocking row the human may carry forward. |

**Classification ties at `high` severity → `deferred to human`**, mirroring the debate rule: a `high` finding the lead cannot confidently place as fact or opinion is never closed by a `judged:` row — it is deferred (outcome `deferred:tie`, non-blocking), surfaced in the delivery comment, and the human decides. (`bug` / `silent-failure` / `security` findings with a demonstrated defect are facts by construction and can never be classed opinion.)

**Answering a question can leave a residue.** When the answer reveals that shipped code is wrong under the chosen semantics (e.g. "decide whether an empty filter means all or none" → answered "all" → the current none-behavior is now a defect), the residue is reclassified as **unquestionable** and reported as an `issue-candidate` row stating the decision ("make an empty filter select all rows"), never as the original question. Answers must never bury real defects.

**Operator-taste questions are never decided on the operator's behalf.** A question whose answer is product semantics rather than engineering fact ("should a disabled account keep its existing records visible?") is **not** answered by the loop: verdict `deferred to human`, one row in the delivery comment carrying the question and the lead's recommended reading, for the human to decide at the merge gate. The loop never asks and never assumes, it defers (outcome `deferred:taste:<lead reading>` — non-blocking, see the verdict vocabulary).

**Bounds.** The triage raises no `AskUserQuestion`. At most ONE batched triage `advisor()` call per review, in addition to the matrix-row call and never in fix rounds (the fix loop's per-round sizing call and the advisor round's grant call are separate bounds).

**The burden of proof is on the finding**, mirroring the debate rule: when the lead cannot state the fact in one imperative sentence with a citation that exists on the PR's head, it is not unquestionable — it is a question or an opinion and takes that lane. `ds-gap` / `ds-intent` findings are unquestionable by construction (a probe-evidenced deviation): they skip the table and always report as `issue-candidate` rows.

This is **not a scope addition**: these rows never enter EXEC.md and never widen the PR. The delivery comment is where the discussion lives.

**Read-only mode runs the identical triage**: a human-owned PR gets zero repo side effects beyond the delivery comment.

## Delivery evidence — two files the receipt points to

The lead writes two files and records them in the receipt's `evidence`. They live under `evidence/` in the cycle folder (the CWD in a run without one); a second PR's go under `evidence/<owner>__<repo>__<n>/`.

| File | Written | Content |
|---|---|---|
| `gates.md` | started empty (`>`) when the preflight probe's section is written, then one section appended (`>>`) when each later suite run of this review finishes | `## <preflight \| round <n>>`, then the lines `command: <runner>`, `head: <sha>`, `result: <the test_run or tests_after value>`, `raw: <its raw output file>`, and the last 20 lines of the sanitized output in a fenced block. A reused run names its `suite_runs[]` entry (`at`) instead; a probe that never ran records its state alone |
| `pr-snapshot.md` | rewritten right before every delivery comment, posted or edited after an extra round | a first line `PR <url> · head <sha> · <iso>` (the receipt's `head`, the time a clock reading), then the sanitized PR body at that head |

**The recipe: raw output to a file, the whole of it sanitized, then cut.** The raw file of a suite run is the one its timebox wrote, and its path stays in the receipt (`test_run.output`, `rounds[].tests_output`):

```bash
set -eo pipefail
# a gates.md section, from its run's <suite-raw>
if ! python3 <PLUGIN_ROOT>/scripts/cortex_sanitize.py < <suite-raw> | tail -n 20 > <tail>; then
  echo 'sanitize failed: output withheld' > <tail>   # never the raw text
fi
test -s <tail> || echo 'no output' > <tail>
# the snapshot; under set -e a failed step writes no snapshot and no evidence key
gh pr view <num> --json body -q .body > <body-raw>
python3 <PLUGIN_ROOT>/scripts/cortex_sanitize.py < <body-raw> > <body>
```

`--limit` is never used here: a cut before the tail would keep the head of the output. The receipt's `evidence` key is written only after both files exist and are non-empty. The files never hold an environment value, a token or a credential.

## Ship & ready (cycle-tail mode)

- Ship = commit pending work (commit-conventions) → push (`-u` on first) → `gh pr create --draft` with title/body per `<PLUGIN_ROOT>/skills/commit-push-pr/references/pr-conventions.md`.
- Push rejected non-fast-forward → fetch and inspect the remote branch first; if human commits are present, **stop and hand back** — never force-push, never rebase over them.
- **E2E, once at the terminal head** (`e2e` in the receipt). When the repo has an E2E suite (named by its CLAUDE.md or PLAN.md, a `test:e2e`/`e2e` script, a Playwright or Cypress config, a Makefile `e2e` target) and the diff is not markdown-only, run it at the head the loop converged on, timeboxed as in preflight §6: a CI job that skips drafts cannot see it. A failure seeds findings like a suite failure (preflight §6) and enters the fix loop within the cap, and the new terminal head runs it again. `env-blocked` (no browser, service or credential here) and `none` are recorded and do not stop the delivery.
- Converged: post delivery comment → `gh pr ready <num>` → verify `gh pr view --json isDraft` shows `false`. When preflight found required status checks: skip the flip, delivery comment header reads `converged (ready blocked by required checks)` — terminal state 3.
- **Converged, and the approved scope ends at a draft PR** (cycle-tail mode, and a standalone-draft run from a cycle folder — `folder:<name>`, or a CWD holding the cycle's `PLAN.md` — so a re-review of the cycle's own draft PR, after a fix pushed for a deviation or an aborted inline review, keeps it draft too): when PLAN.md's Scope **explicitly** requires the PR to stay draft (e.g. "A draft PR … Leave the PR open, unmerged, and undeployed"), skip the flip — the delivery comment header reads `converged (kept draft by approved scope)` and quotes the line — terminal state 4. Never inferred: no quotable line → flip as usual. Convergence comes first (a non-converged loop is `draft-needs-human` whatever the scope says), and the scope wins over required checks (no flip is attempted, so the checks are not what holds it; the comment still mentions them).
- Not converged: post delivery comment → PR stays draft. Done is done — don't loop past the cap: the advisor round (§ "Advisor round") and a `Review round` grant are its only extra rounds.
- **A second PR of the same cycle** follows these same rules from its own run (`cortex:review pr:<n> folder:<cycle>`), with its receipt at the per-PR location (§ "Receipt"). The cycle's scope line that keeps the first PR draft keeps this one draft too. PLAN.md or EXEC.md must cite the PR (its URL, `owner/repo#N`, or `#N` in the cycle's repository) so `/cortex:end`'s merge gate sees it.
- **Record the terminal state** in the same receipt write that sets `status: complete`: `terminal` from the final fresh `gh pr view --json isDraft,state`, in this precedence — `draft-needs-human` (not converged) · `draft-kept-by-scope` (converged, flip skipped because PLAN.md's Scope ends at a draft PR; also write `terminal_reason` with the quoted line) · `draft-blocked-by-checks` (converged, flip skipped for required checks) · `ready` (the flip verified `isDraft: false`); read-only mode writes `read-only`. A partial/aborted receipt carries `terminal: null`. Use exactly these keys and values — readers never parse prose (a receipt without `terminal` reads as `unknown`, never ready, never converged).

## Bounds recap (the numbers that keep this honest)

- 2 fix rounds, hard (plus at most one round the advisor grants, § "Advisor round", and the extra rounds a `Review round` answer grants, each scoped to the blocking items). After the cap, only `high`, floor-area and `medium`+ this-loop-regression items block; the rest, a `low` this-loop regression outside the floor areas included, become follow-up rows. ≤1 sizing `advisor()` call per round. ≤1 grant `advisor()` call per review (it is the granted round's sizing call). 1 fix-author per disjoint file group, gates once per round after every group lands. 1 defender per debated finding. Triage: ≤1 batched advisor call per review. Re-run scope = affected reviewers only. 1 delivery comment. Fresh `isDraft` before every round. Receipt after every transition. Test suite: 10 min timebox per run (preflight + once per fix batch), repo-configured tooling only.
